================================================================================
BUG-001: Transfer API allows overdraft — no balance validation
================================================================================
Severity : High
Endpoint : POST /services/bank/transfer
Test     : Transfer > amount exceeding balance > error response and balances unchanged

Description
-----------
The transfer endpoint accepts amounts that exceed the source account's available
balance. Instead of rejecting the request with a 4xx status, it returns HTTP 200
and commits the transaction, silently driving the account into a negative balance.

Steps to reproduce
------------------
1. Obtain an account with a known positive balance (e.g. $100).
2. POST /services/bank/transfer?fromAccountId=<id>&toAccountId=<other>&amount=<balance * 2>
3. Observe: HTTP 200 "Successfully transferred $<amount> from account #<id>..."
4. GET /services/bank/accounts/<id>  →  balance is now negative.

Expected behavior
-----------------
HTTP 400 (or 422) with an error message such as "Insufficient funds".
Source and destination balances remain unchanged.

Actual behavior
---------------
HTTP 200. Source balance decreases below zero; destination balance increases.

Evidence (manual probe on 2026-05-20)
--------------------------------------
Account 13677 had balance $50.
POST amount=$9999  →  200 OK
GET account 13677  →  balance: -$9949


================================================================================
BUG-002: Transfer API accepts negative amounts — reverses money flow silently
================================================================================
Severity : High
Endpoint : POST /services/bank/transfer
Test     : Transfer > negative amount > API returns 4xx and no transaction created

Description
-----------
The transfer endpoint does not validate that the amount is a positive number.
Submitting a negative amount causes funds to flow in the opposite direction
(from toAccountId → fromAccountId), bypassing any intentional authorization
from the "destination" account holder. The server responds HTTP 200 and records
a transaction, exposing users to unauthorized fund extraction.

Steps to reproduce
------------------
1. Have two accounts A and B.
2. POST /services/bank/transfer?fromAccountId=A&toAccountId=B&amount=-100
3. Observe: HTTP 200 "Successfully transferred $-100 from account #A..."
4. GET /services/bank/accounts/A  →  balance increased by $100.
5. GET /services/bank/accounts/B  →  balance decreased by $100.

Expected behavior
-----------------
HTTP 400 (or 422) with an error message such as "Amount must be positive".
No transaction is created; balances remain unchanged.

Actual behavior
---------------
HTTP 200. Funds flow from B → A (reverse of what the request states).
A transaction entry is created in both accounts.

Evidence (manual probe on 2026-05-20)
--------------------------------------
Account 13677 (from), account 13788 (to), amount=-50.
POST  →  200 OK
13677 balance went UP by $50; 13788 balance went DOWN by $50.

================================================================================
BUG-003: Registration creates account with $515 balance but no transaction record
================================================================================
Severity : Low
Endpoint : GET /services/bank/accounts/{id}/transactions
Test     : GET /accounts/{id}/transactions > response matches Transaction interface shape

Description
-----------
When a new customer registers, Parabank creates a default CHECKING account
seeded with a $515 balance. However, no transaction is recorded for this
initial deposit. Calling GET /accounts/{id}/transactions on this account
immediately after registration returns an empty array ([]), even though
the account clearly holds funds.

Steps to reproduce
------------------
1. Register a new user via the UI.
2. Retrieve the customer's accounts: GET /services/bank/customers/{id}/accounts
3. Note accounts[0].balance = 515.
4. GET /services/bank/accounts/{accounts[0].id}/transactions
5. Observe: response is [] (empty array).

Expected behavior
-----------------
An "Initial deposit" transaction entry should exist explaining the $515 balance.
The response should contain at least one Transaction object.

Actual behavior
---------------
Empty array returned. The $515 balance has no traceable origin in the
transaction history.

Evidence
--------
Discovered via test execution on 2026-05-27.
Any account used only for the initial balance (no transfers in or out)
returns an empty transaction list.

================================================================================
BUG-004: POST /createAccount response returns balance 0 instead of actual balance
================================================================================
Severity : Medium
Endpoint : POST /services/bank/createAccount
Test     : N/A (observed during test setup — api.openNewAccount)

Description
-----------
When a new account is created via the API, the JSON response body contains
"balance": 0.  In reality, Parabank seeds every new account with a $100
opening deposit, which is correctly reflected in the UI and in a subsequent
GET /accounts/{id} call.  Tests that rely on the response balance (e.g. to
decide whether a payment can be made) will therefore read the wrong value.

Steps to reproduce
------------------
1. POST /services/bank/createAccount?customerId=<id>&newAccountType=0&fromAccountId=<id>
2. Inspect the JSON response body — "balance" field is 0.
3. Open the app in the UI or call GET /services/bank/accounts/{newId}
4. Observe: balance is $100.

Expected behavior
-----------------
The response body should reflect the actual post-creation balance ($100),
or at minimum match what GET /accounts/{id} returns immediately after creation.

Actual behavior
---------------
Response body always contains "balance": 0 regardless of the opening deposit.
A separate GET request is required to read the real balance.

Workaround
----------
Do not use the balance from the POST /createAccount response.
Always fetch the account via GET /accounts/{id} when the actual balance is needed.

Evidence
--------
Discovered on 2026-05-27 during test development.
POST response  →  { ..., "balance": 0 }
GET /accounts/{newId}  →  { ..., "balance": 100.00 }
